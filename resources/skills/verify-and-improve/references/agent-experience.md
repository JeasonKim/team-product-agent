# Agent 体验验证

## 两个角色

改进 Agent 观察、诊断和修正产品；被测 Agent 在产品真实入口接收普通用户需求。运行器可以用脚本代替重复点击，但不得替被测 Agent 选择场景、生成业务配置或直接调用最终动作来冒充对话成功。

## 简单输入，独立验收

- 输入来自用户原话或同等信息量的口语表达；详细验收要求保存在测试侧，不注入被测上下文。
- 需要多轮对话时，模拟用户只提供普通用户知道的信息，不提示工具名、字段名或正确调用路径。必要追问可以是正确行为，不把零追问当作普遍指标。
- 指定模型、产品提示词、工具和权限与真实使用保持一致；每次试验使用独立会话及可隔离的数据，不能继承前次成功的隐藏状态。
- 开发用例之外保留若干不同说法或相邻场景，在候选改动完成后验证，避免只对固定句子有效。

## 观察重点

| 维度 | 证据 |
| --- | --- |
| 结果 | 实际业务状态与交付物符合目标，不只检查回复或某次工具成功。 |
| 理解 | 保持用户意图；合理默认与关键追问匹配场景。 |
| 流畅 | 关注重复调用、误用工具、无关探索和停滞；不强制唯一工具顺序。 |
| 成本 | 按成功交付统计总耗时、可获得的 token 和工具调用，保留失败成本；区分模型等待与产品执行。 |
| 稳定 | 同一版本下重复与不同表达的表现；修好一类场景后检查相关旧场景。 |

优先依据工具参数、返回值、可见消息和真实状态诊断，不依赖不可见的模型内部推理。区分产品或工具问题、模型行为、环境异常与验收器错误；例如工具返回过大可能需要调整返回契约，而非继续堆叠提示词。

模拟、真实宿主、真实账号与外部写入分别记录验证范围。模拟可以支持快速迭代；最终结论与实际覆盖的范围一致。
